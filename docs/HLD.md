# 金融数据分析 Agent 高层设计

## 1. 目的

本项目面向两个目标：

1. **面试展示**：展示 MCP 工具化、金融数据审计、错误语义、确定性计算和受控 Agent
   等工程能力。
2. **个人使用**：提供中国基金、指数、ETF 和 A 股的数据分析与关联说明，辅助研究，
   不替用户决策。

当前功能优先级是将已实现的基金、指数、ETF 和个股分析能力组织为可持续更新的数据
工作台，并在列表、详情和筛选结果中接入受控 Agent。组合分析、策略回测、持仓管理和
生产级平台暂不进入当前范围。

## 2. 产品定位

项目是“**可信投研数据工作台 + LangGraph 受控研究 Agent**”，不是：

- 自动交易系统；
- 收益预测或荐股系统；
- 大而全的金融终端；
- 多 Agent 自由协作平台；
- 量化因子、组合优化或回测平台。

Agent 的价值不在于产生新的金融事实，而在于：

- 理解用户研究问题；
- 理解当前页面、筛选条件和已选标的；
- 选择已注册的 MCP 工具；
- 将基金、指数、个股和外部背景结果按语义关联；
- 区分事实、历史统计、关联关系和限制；
- 用可追溯的方式解释结果。

## 3. 核心原则

### 3.1 市场事实只能来自工具

以下内容只能来自通过 Schema、时效和 `frame_sha256` 审计的 AKShare 结果：

- 基金净值、ETF/股票价格、指数点位；
- PE、PB、收益率、波动率、回撤和历史分位；
- 申购、赎回、限额和交易状态；
- 基金、股票和指数是否存在及其规范代码。

模型不得生成、补齐、插值、前向填充、修复或改写这些内容。

### 3.2 计算必须确定性

收益、波动、回撤、历史分位、ETF 溢价等由 Skill 的固定公式计算。Agent 只能解释
已经计算好的结果，不能在自然语言中重算。

### 3.3 关联不等于因果

Agent 可以说明两个已审计事实同时出现或可能相关，但必须使用：

- “同时存在”；
- “历史上表现为”；
- “可能与……有关，需要更多证据确认”；
- “不能据此证明因果关系”。

禁止使用“因为 A，所以 B 必然发生”这类无证据因果表达。

### 3.4 失败语义必须明确

必须区分：

- `NOT_FOUND`：目录查询成功但无实体；
- `AMBIGUOUS`：有多个候选，需要用户确认；
- `UNSUPPORTED`：实体可能存在，但当前接口不支持；
- `UPSTREAM_ERROR`：数据源失败，无法判断；
- `STALE_DATA`：数据存在但时效不满足要求。

上游失败时只能回答“当前无法确认”，不能回答“该标的不存在”。

## 5. 目标架构

语言分工：Go 负责网页后端（Dashboard BFF、静态托管、Agent SSE 代理），Python 负责
Agent、MCP、Skill 和全部金融计算与审计。二者通过 MCP 协议和 Agent API 连接，边界与
透传规则见 [Go/Python 透传契约](GO_PYTHON_CONTRACT.md)。

目标产品包含两条明确分离的读取链路：

1. **数据工作台链路**：列表、图表和详情直接消费结构化数据，不经过模型。
2. **Agent 研究链路**：结合用户问题和页面上下文调用固定 LangGraph，再解释已验证事实。

```text
React 数据工作台
   |
   v
Go 网页后端（BFF；下一阶段）
   |-- 静态托管、路由、缓存、限流
   |
   +-- 数据请求（Go 作为 MCP Client；不调用模型）
   |     -> Fund Advisor MCP (Python)
   |     -> AKShare Skill (Python)
   |     -> 结构化、已审计数据（原样透传 ToolEnvelope）
   |
   `-- 问题 + 受控页面上下文（SSE 反向代理）
         -> Agent API (Python；临时会话 + SSE)
         -> LangGraph Agent（固定图 + 响应门禁）
         +-> Fund Advisor MCP -> AKShare Skill
         `-> Web Research MCP -> 公网搜索/页面/文档

条件性后续（当前未实现）：
Update Worker -> Fund MCP / Skill -> PostgreSQL 已审计快照
Go BFF / Dashboard 读路径 -> PostgreSQL 已审计快照
Redis -> 多副本共享缓存、更新锁或限流
```

无论是否引入快照存储，Fund MCP / Skill 都是市场事实进入系统的唯一审计入口。Go 后端只
做取数、聚合、缓存和代理，不重算或改写任何市场数值；数据库只保存已经通过 Schema、
时效和内容指纹校验的结果，不能绕过工具审计成为新的事实来源。

### 5.1 Fund Advisor MCP

| 工具 | 作用 |
| --- | --- |
| `fund_search` | 搜索基金候选，不自动选择份额 |
| `fund_status` | 查询申购、赎回或场内交易状态 |
| `fund_analyze` | 分析基金历史收益、风险和持有体验 |
| `fund_profile` | 查询类型、经理、费用、规模和资产配置 |
| `fund_rating` | 按代码查询第三方评级 |
| `index_valuation` | 指数 PE TTM / PB 历史分位 |
| `stock_valuation` | A 股 PE TTM / PB / 前复权价格历史 |
| `fund_compare` | 比较两到五只基金并提示口径差异 |
| `interface_audit` | 审计真实接口和 Schema |

MCP 负责参数契约、超时、缓存和统一 `ToolEnvelope`，不得修改 Skill 数值。

### 5.2 Web Research MCP

| 工具 | 作用 |
| --- | --- |
| `web_search` | 搜索非数值背景 |
| `web_fetch` | 安全读取网页正文 |
| `document_read` | 按用户 URL 读取 HTML、文本或 PDF |

Web 结果固定 `numeric_allowed=false`。它可以补充政策、公告或文档背景，但不能确认
市场实体，也不能提供或覆盖市场数值。

启用 Web Research 后，基金和股票单标分析固定追加“研究/媒体文章”和“博主/社区观点”
两类可选搜索。来源类别由域名和标题规则确定，仅用于结果分组，不代表账号身份或内容
真实性已经核验。可选搜索失败时保留市场分析并标记 `partial_result`；市场工具失败时
不得用 Web 结果替代。

### 5.3 LangGraph Agent

Agent 使用 LangGraph `StateGraph` 实现固定、有向、可测试的状态图。选择 LangGraph 是为了
显式表达节点、条件边和终止状态，不是为了增加模型自治能力。

第一版固定闭环：

```text
QUESTION
  -> CLASSIFY
  -> PLAN_REGISTERED_TOOLS
  -> CALL_MCP
  -> VALIDATE_TOOL_ENVELOPES
  -> BUILD_RESEARCH_SYNTHESIS
  -> VALIDATE_RESPONSE
  -> RENDER_ANSWER
  -> ANSWER
```

条件边只允许进入以下终止分支：

```text
AMBIGUOUS       -> need_clarification
NOT_FOUND       -> not_found
UNSUPPORTED     -> unsupported
UPSTREAM_ERROR  -> cannot_confirm
STALE_DATA      -> stale_data
PARTIAL_RESULT  -> partial_result
```

边界：

- 图结构、工具白名单、错误映射和放行条件由代码定义；
- 模型只参与受限意图补充和结构化研究综合，不决定市场事实是否有效；
- Agent 只能通过 MCP Client 调用工具，不直接 import `FundAdvisor`；
- 图不配置数据库 checkpoint、长期会话或跨会话 Memory；
- 不使用 LangChain AgentExecutor、开放式 ReAct、动态工具规划、多 Agent 或自治反思循环；
- 图保持无环；失败后由用户重新发起，不在图内无限重试。

### 5.4 Agent API 与 Web

Web 通过 Agent API 执行研究问答，不复制工具规划、金融计算或门禁。Agent API 使用
SSE 输出：

```text
session -> status* -> result | error -> done
```

临时会话只在进程内保存最近消息、上一轮实体和意图，用于处理“它的风险呢”这类追问。
会话有 TTL、数量和消息上限；页面刷新、会话过期或服务重启后可以清空。
历史消息不能成为市场事实，也不引入登录、数据库或长期记忆。

当前 React 页面参考 GPT、Claude 的聊天布局，已包含临时会话、消息流、研究进度和
输入框。下一阶段将其调整为数据工作台：主界面负责浏览数据，Agent 以全局入口和页面内
抽屉存在。

已经实现的 CLI 继续调用同一个 Agent API，仅作为兼容和开发调试入口。后续不为 CLI
增加页面对应功能、独立业务逻辑或专项产品交互；新增产品能力以 Web 为唯一验收界面。

### 5.5 数据工作台与页面上下文

第一版数据工作台包含：

| 页面 | 主要内容 |
| --- | --- |
| 总览 | 各数据集更新时间和异常、指数估值概览、基金/ETF 风险提示、候选和研究动态 |
| 基金与 ETF | 分类、搜索、筛选、排序、费用、规模、历史表现、交易状态和详情 |
| 股票 | 候选规则、估值、财务质量、行业比较和详情 |
| 指数 | PE/PB 历史分位、专业终端式历史双图、估值看板、指数详情和关联基金 |
| 研究动态 | 研究机构、财经媒体和博主社区链接，保留来源、分类和发布时间 |

列表和详情中的金融数值直接来自结构化 API 响应，前端不得让模型从文本中提取后再展示。
数据工作台由 Go 网页后端提供：Go 作为 MCP Client 聚合 Python Fund MCP 的 `ToolEnvelope`
并原样透传审计字段，不重算或改写任何市场数值（透传细节见
[Go/Python 透传契约](GO_PYTHON_CONTRACT.md)）。
每个数据块必须携带 `as_of`、`queried_at`、数据状态、warning 和可用的 `audit_ref`。
页面不得使用统一的“实时”标签覆盖不同数据源口径：

- 盘中数据标明查询时间；
- 日频或 T+1 数据标明数据日期；
- 过期数据标记 `STALE_DATA`；
- 上游失败标记当前无法确认，不沿用旧值伪装最新数据。

PE/PB 页面采用两级展示：

1. 总览和列表展示当前 PE/PB、各自历史分位和数据日期，便于扫描；
2. 指数和个股详情必须展示历史曲线，不能用当前值卡片或“高估/低估”标签替代。

历史图的信息组织参考 Wind 深度资料，但数据仍来自通过审计的 AKShare Skill：

- 指数默认展示 PE TTM 和 PB 上下两张同步历史图；
- 个股分别展示前复权价格、PE TTM 和 PB，三者不合并为双轴综合信号；
- 默认观察十年，并只展示本次结果实际可用的 3/5/10/20 年窗口；
- 展示当前值、历史分位、均值、中位数、最高、最低、P20/P80 和均值 ±1 标准差；
- 两张估值图共享时间范围，支持 tooltip、十字准星、缩放和窗口切换；
- 统计量使用完整日频样本，曲线只连接工具返回的真实显示点；
- 显示 `source_observations`、`displayed_points`、实际起止日期、来源和审计引用；
- PE 或 PB 单侧缺失时只展示可用侧并解释缺失，不用零值补齐。

“参考 Wind”仅指信息层次和交互体验，不表示 Wind 数据源，不复制 Wind 商标、配色或
专有界面，也不要求绕过商业授权获取 Wind 数据。

页面调用 Agent 时传递受控上下文，而不是整页文本：

```text
page_type
selected_entities
active_filters
sort
visible_fact_refs
user_question
```

Agent 仍须通过注册工具重新确认所需市场事实。页面上下文只能帮助理解指代和研究范围，
不能直接升级为可信事实。

### 5.6 Agent、模型与工具的职责

项目采用“模型处理模糊语言，Agent 控制流程，工具提供事实”的分工：

| 角色 | 负责 | 不负责 |
| --- | --- | --- |
| 数据工具 | 查询和校验市场数据，执行确定性计算 | 理解开放式问题、生成研究结论 |
| Agent | 识别问题、选择固定工作流、调用工具、处理错误、执行门禁 | 生成市场事实、自由扩展工具和流程 |
| 模型 | 解释已验证事实、比较非结构化观点、组织研究表达 | 决定金融数字、错误状态、工具权限和最终放行 |

当前实现中，Agent 已承担固定编排、MCP 调用、结果校验和响应门禁；模型通过一次结构化
调用生成研究问题、支持/反对/未知证据分组、关联说明和下一步研究清单，并可选在规则未
提取到实体时补充意图。因此当前模型是“受约束的研究解释器”，不是自主投资决策者。

根据明确的用户期限、仓位和风险承受能力调整解释重点仍是后续能力；当前尚未建立独立的
用户约束输入契约。

上述能力必须消费已验证事实并输出结构化结果。模型仍不能修改图状态、创建工具、生成
金融数值或输出确定性交易指令。

### 5.7 数据刷新、缓存与存储

#### 工作台第一阶段（下一阶段，尚未实现）

- Dashboard API 按请求调用 Fund MCP，并复用 MCP 的有界进程内 TTL 缓存；
- 临时会话使用 Agent API 进程内存；
- 不部署 PostgreSQL、Redis、消息队列或 LangGraph 数据库 checkpoint；
- 容器重启后缓存和临时会话清空，不影响市场事实来源。

#### 条件性后续

当基金/指数列表、历史快照和横截面筛选的查询成本形成明确瓶颈后，可增加：

```text
定时 Update Worker
  -> Fund MCP / AKShare Skill
  -> 审计与时效校验
  -> PostgreSQL 已审计快照
  -> Dashboard API
```

PostgreSQL 只保存规范实体、结构化指标、`as_of`、查询时间、Schema 版本、来源和
`frame_sha256`。写入必须采用新快照校验成功后再原子切换；上游失败不能覆盖最近一次成功
快照，页面同时展示“最近成功日期”和“本次更新失败”。

Redis 只在以下需求实际出现时引入：

- Agent API 或 MCP 多副本需要共享缓存；
- Update Worker 需要分布式锁和防重复执行；
- Dashboard API 需要跨实例热点缓存或限流。

Redis 不存长期历史，不作为市场事实源，也不用于恢复跨会话长期记忆。当前单副本 Compose
没有这些需求，因此不提前增加 Redis。

## 6. 基金与个股数据分析

### 6.1 基金分析

基金分析按以下顺序组织：

1. **实体与产品**：代码、名称、类型、经理、基准、费用、规模。
2. **数据口径**：场外累计净值、ETF/LOF 历史价格或货币基金收益率。
3. **历史表现**：区间收益、年化波动、下行波动、最大回撤和修复时间。
4. **持有体验**：最长水下期、月度收益统计、滚动观察期收益分布。
5. **底层估值**：仅当跟踪指数可精确解析时解释指数 PE/PB。
6. **交易因素**：申赎状态、场内价格、IOPV 和溢价。
7. **限制**：数据日期、样本长度、接口缺失和不可比项。

基金净值历史位置不是估值。主动基金不得因为净值处于历史低位就被描述为“低估”。

### 6.2 指数分析

PE TTM 和 PB 分别计算、分别解释：

- PE 反映相对盈利的历史估值位置；
- PB 反映相对净资产的历史估值位置；
- 两者口径不同，不平均、不合成“综合估值分”；
- 历史分位只说明历史位置，不预测收益。

指数详情必须消费 `charts.pe_ttm` 和 `charts.pb` 的 `chart_series`、`reference_lines`
及 `window_statistics` 渲染历史双图。摘要中的当前值和分位不能替代曲线。

### 6.3 个股分析

个股分析包含：

- PE TTM 当前值与历史分位；
- PB 当前值与历史分位；
- 前复权价格历史；
- 数据可用性、观察区间和时效。

价格、PE 和 PB 使用独立序列。价格上涨与估值分位变化可以关联说明，但不能直接写成
盈利改善、资金推动等因果结论，除非有额外工具证据。

个股详情必须将价格、PE、PB 渲染为三个独立历史视图，禁止为了视觉简化只保留当前
PE/PB 或把价格与估值合成未经定义的综合曲线。

### 6.4 比较分析

比较前先检查：

- 基金类型；
- A/C 类等份额类别；
- 净值、价格或收益率口径；
- 跟踪指数或业绩基准；
- 观察区间和数据日期。

不可比时输出差异，不计算总分。

## 7. LangGraph Agent 关联说明设计

### 7.1 输入

关联说明只能消费成功的 `ToolEnvelope`，并保留：

- 工具名和请求参数；
- 规范实体；
- 指标、单位和日期；
- 数据审计；
- 数据警告和错误。

### 7.2 输出结构

```text
事实
  - 原样展示工具事实

关联说明
  - 描述多个事实如何共同影响研究理解
  - 标明这是关联，不是因果

限制
  - 数据日期、缺失接口、不可比口径和历史统计局限

参考结论
  - 条件式表达，不给确定性交易指令
```

### 7.3 允许的关联

- 产品类型与历史风险特征；
- 基金与精确跟踪指数的估值关系；
- ETF 溢价与场内执行风险；
- 个股价格历史位置与 PE/PB 历史位置；
- 多只基金的收益、风险、费用和基准差异；
- 数据质量对结论可信度的影响。

### 7.4 禁止的关联

- 用网页文本覆盖市场工具；
- 用名称猜测基金跟踪指数；
- 把净值低位写成估值低位；
- 把同时发生写成因果关系；
- 从历史分位推导未来收益概率；
- 用缺失字段生成综合评分；
- 给出“必买、必卖、稳赚、抄底”等指令。

## 8. 面试工程亮点

项目应重点展示：

1. **MCP 标准化边界**：工具发现、Schema、stdio/HTTP 传输和 Client/Server 分工。
2. **金融数据契约**：实体解析、Schema、时效、`frame_sha256` 和字段口径。
3. **错误模型**：不存在、歧义、不支持、过期和上游失败分离。
4. **确定性计算**：模型不参与收益、回撤、分位和溢价计算。
5. **数据源隔离**：市场事实 MCP 与 Web 背景 MCP 分离。
6. **上游治理**：多搜索供应商降级、AKShare 接口降级、SSRF 防护。
7. **可测试性**：固定夹具验证公式与错误语义，真实 `audit` 验证上游。
8. **LangGraph 受控编排**：固定节点、条件边、工具白名单和响应校验，不追求自由自治。
