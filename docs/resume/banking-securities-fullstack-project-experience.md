## 简历可直接使用版

### 金融数据研究与分析平台

**技术栈：** Java 21、Spring Boot、Spring MVC、MyBatis、MySQL、Redis、React、
TypeScript、ECharts、Docker

**项目描述：**

面向基金、ETF、指数和股票等金融产品的查询与研究场景，完成免登录公开访问的前后端
一体化数据平台。后端负责金融数据接口聚合、匿名互动数据管理、访问限流及流式接口；前端提供
行情图表、估值分析、趋势对比、申购状态和海外基金限额等可视化功能，并适配 PC、平板和
移动端，同时提供智能问答入口。

**主要工作：**

- 使用 Spring Boot 开发统一后端服务，提供基金、ETF、指数、股票和匿名互动等 REST
  接口；对接内部数据计算服务，统一处理参数校验、异常返回和数据状态。
- 使用 Java 21 虚拟线程和 `CompletableFuture` 并行查询多个独立数据模块，结合并发
  上限、分批提交及连接/读取超时，限制慢接口对整体服务的影响。
- 使用 MyBatis 和 MySQL 完成匿名投票及按钮反馈持久化，通过事务、联合唯一索引和写
  冲突重试处理同一客户端的重复提交；使用 Redis Lua 实现固定窗口接口限流。
- 建立统一金融数据响应格式，保留数据来源、查询时间、异常信息和数据快照指纹；
  对上游异常、数据过期、标的不存在和部分数据可用等情况分别处理，避免错误数据进入页面。
- 使用 React、TypeScript 和 ECharts 开发高密度金融数据面板，实现多图联动、时间范围
  筛选、趋势表格排序、价格与份额对比、深浅主题及海外基金申购限额展示。
- 封装按钮、链接和选择器等公共组件及统一样式变量，处理请求超时、取消、重复请求合并、
  加载与错误状态，并通过 Playwright 校验多个桌面和移动端视口下的布局与文字显示。
- 使用 SSE 实现分析过程和结果的流式展示；通过 Docker Compose 编排 Java、数据
  服务、MySQL、Redis 等 7 个服务，并通过后端单元测试、接口测试和前端自动化测试验证
  主要功能。

## 低代码 Agent 接入方案

### 项目主次关系

- **主项目**：金融数据面板及 Java 后端，负责数据查询、匿名互动、缓存、持久化、审计和接口。
- **辅助能力**：低代码 Agent，负责问题理解、流程编排和答案组织。
- **数据边界**：Agent 只能调用后端提供的受控接口，不能直连数据库，也不能自行生成行情、
  估值、限额等金融数据。

### 推荐的最小链路

```text
React 对话窗口
  -> Java 智能问答接口
    -> 低代码 Agent 平台
      -> Java 数据工具接口
        -> 内部金融数据服务
    <- 流式回答
  <- SSE 返回前端
```

Java 后端继续负责：

1. 匿名客户端标识、接口限流和防重复提交；
2. Agent 调用凭证保管；
3. 可调用的数据工具白名单；
4. 匿名会话标识、请求编号和调用日志；
5. 数据结果的来源、时效和异常校验；
6. SSE 流式转发、超时和失败处理。

低代码平台负责：

1. 问题分类和工作流编排；
2. 调用 Java 提供的查询工具；
3. 根据已返回的数据生成说明；
4. 维护提示词和基础对话流程。

### 简历写法

在低代码 Agent 真正接通并完成验证前，只写：

> 为智能问答能力预留统一数据接口和 SSE 流式返回链路。

完成接入后可以改为：

> 接入低代码智能问答工作流，将基金、ETF、指数和股票查询接口封装为受控工具，并通过
> Java 服务统一处理接口限流、数据校验、调用日志和 SSE 流式返回。

不要写“自主研发 Agent 平台”“多智能体系统”或“完整智能投研平台”。

## 后端当前缺少的能力

### 第一优先级：建议补齐

1. **匿名互动的防刷与幂等**
   - 当前已使用浏览器生成的匿名客户端 UUID、数据库唯一约束和接口限流处理投票及按钮
     反馈，不需要引入登录、JWT 或角色权限。
   - 仍需考虑匿名标识被清除或伪造、同一来源批量提交等情况，可增加服务端签名标识、IP
     频率限制和异常提交统计。

2. **匿名评论与内容治理**
   - 已实现 ETF 维度的匿名评论，包含长度限制、5 分钟限频、10 分钟重复内容拦截、匿名
     别名和 `published/hidden` 状态；接口不返回客户端 UUID。
   - 当前仍缺少敏感内容检测、举报和管理端隐藏操作，正式公开运营前需要接入审核流程。

3. **核心业务数据落库与查询**
   - 当前 MySQL 主要保存自选和互动，行情与估值仍以实时调用外部数据服务为主。
   - 建议增加产品基础信息、行情快照、数据同步批次和异常记录等表，设计唯一索引、查询
     索引、分页和数据保留策略。
   - 补齐后才能更有底气描述金融数据后台，而不只是接口聚合项目。

4. **数据库与缓存集成测试**
   - 当前 Java 测试以 MockMvc、MockWebServer 和 Mock 为主，缺少真实 MySQL/Redis
     环境下的集成测试。
   - 建议使用 Testcontainers 覆盖数据库迁移、唯一索引并发冲突、Redis Lua 和事务回滚。

### 第二优先级：按业务需要补齐

5. **热点数据缓存**
   - 当前 Redis 主要用于限流，金融数据缓存位于 Python 进程内。
   - 可为查询频繁、更新周期明确的产品信息或行情快照增加 Redis 缓存，并明确 TTL、失效、
     空值缓存和源数据更新后的刷新策略。

6. **定时数据同步**
   - 当前数据大多在用户请求时实时获取，缺少交易日定时同步、失败重跑和批次状态。
   - 可先使用 Spring 定时任务完成每日数据刷新；只有出现任务积压、多消费者或可靠投递
     需求时再考虑消息队列。

7. **统一日志与链路定位**
   - 当前已有健康检查和基础指标，但缺少贯穿 Java 与 Python 服务的请求编号、结构化日志
     和调用耗时统计。
   - 建议先补请求 ID、接口耗时、下游错误和限流次数，再评估是否引入链路追踪系统。

8. **接口文档和后端持续集成**
   - 建议增加 OpenAPI 接口文档，并在 GitHub Actions 中执行 Java 构建、单元测试和
     Python 契约测试。
   - 当前自动发布主要覆盖前端，后端缺少独立持续集成流程。

### 暂时不建议为了简历加入

- Spring Cloud 全家桶；
- Kafka、RocketMQ 等消息队列；
- 分布式事务框架；
- 分库分表；
- Kubernetes；
- 复杂规则引擎。

这些能力必须由真实的服务拆分、任务积压、事务跨度或部署规模驱动。当前项目优先补匿名
互动治理、评论审核与举报、业务数据落库和真实集成测试，投入产出更高。
