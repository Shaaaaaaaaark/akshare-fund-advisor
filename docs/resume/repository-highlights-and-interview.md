## 一、项目技术画像

Fund Advisor 是一个面向中国基金、ETF、指数和 A 股研究的金融数据工作台，同时包含受控
Agent 问答能力。系统不是传统单体，也不是完整微服务平台，而是以 Java 21 + Spring Boot
3.5 BFF 为唯一公网入口，向内连接 Python Data API、Agent API 和两个 MCP 服务的多服务
架构。Java 负责 HTTP 边界、并发聚合、限流、MySQL 产品数据、静态资源和 SSE 代理；
Python 负责金融数据采集、确定性计算、审计和 Agent 编排。

核心链路对“金融事实可追溯”优先：市场数据必须携带来源、查询时间、Schema 校验结果和
`frame_sha256`，Java 与 React 不重算、不补值。接入层则在部分场景偏可用性：Redis 限流
故障时 fail-open，但 Data API 仍由 Bulkhead 保护。项目当前属于可运行 MVP，具备容器化、
健康检查、指标暴露和多层测试，但没有生产流量、自由文本评论治理、MQ、分布式存储、RAG、线上
告警闭环或性能基准证据。

作为主项目，最适合突出 Java BFF 边界设计、有界并发、错误与审计契约、Redis/MySQL
工程治理；作为次项目，可突出固定 LangGraph、MCP Tool 和 SSE 接入。AI 应用架构匹配度
中等偏高，AI 推理优化和大规模分布式存储匹配度低。

## 二、业务背景重建

### 1. 代码已明确体现的业务事实

#### 事实 1：Java BFF 是唯一公网入口

- **业务事实**：Dashboard、产品数据和 Agent 请求统一进入 Java。
- **证据**：
  - 文件路径：`README.md`、`deploy/compose/compose.yaml`
  - 类 / 方法：`DashboardController`、`AgentProxyHandler.proxy`
  - 接口：`/api/dashboard/**`、`/api/watchlist`、`/api/panel/interactions`、
    `/api/chat/**`
- **可写入简历程度**：高。
- **适配 JD**：Java 后端、AI 应用后端、平台工程。
- **风险边界**：可写“统一入口/BFF”，不写“企业级网关平台”。

#### 事实 2：Java 不生成或改写金融事实

- **业务事实**：Python 返回完整 `ToolEnvelope`，Java 只提取展示元数据并原样透传。
- **证据**：
  - 文件路径：`web-backend/.../facts/ToolEnvelope.java`
  - 类 / 方法：`ToolEnvelope.parse/frameHashes`、`DashboardService.envelopeMeta`
  - 契约：`@JsonRawValue`、`data_audit`、`frame_sha256`
- **可写入简历程度**：高。
- **适配 JD**：核心链路设计、数据平台、AI 应用工程。
- **风险边界**：这是数据可信边界，不是财务审计系统。

#### 事实 3：多数据模块并行聚合且有并发门禁

- **业务事实**：总览与基金产品需要独立调用多个数据模块。
- **证据**：
  - 文件路径：`DashboardService.java`、`DataApiClient.java`
  - 类 / 方法：`overview`、`fundProduct`、`invokeAll`、`callTool`
  - 配置：`DASHBOARD_CONCURRENCY`，默认 4
- **可写入简历程度**：高。
- **适配 JD**：Java 并发、稳定性、服务聚合。
- **风险边界**：没有压测结果，不能写吞吐提升比例。

#### 事实 4：MySQL 保存产品元数据并提供幂等约束

- **业务事实**：自选列表及匿名投票/反馈持久化到 MySQL。
- **证据**：
  - 文件路径：`V1__create_watchlist.sql`、`V2__create_panel_interaction.sql`
  - 类 / 方法：`WatchlistService.create`、`PanelInteractionService.submit`
  - 表：`watchlist_item`、`panel_interaction`
- **可写入简历程度**：高。
- **适配 JD**：Java 业务后端、事务与一致性。
- **风险边界**：不是资金或交易资产一致性。

#### 事实 5：Redis 用于入口固定窗口限流

- **业务事实**：Dashboard、自选和互动接口按客户端地址限流。
- **证据**：
  - 文件路径：`DashboardRateLimitFilter.java`、`RedisRateLimitStore.java`
  - 机制：Lua 原子执行 `INCR + EXPIRE`
  - 配置：默认 120 次/60 秒
- **可写入简历程度**：高。
- **适配 JD**：缓存、中间件、稳定性治理。
- **风险边界**：不是完整网关限流平台，不支持令牌桶或分级配额。

#### 事实 6：Agent 通过 SSE 流式接入

- **业务事实**：Java 透明代理 Agent API 的会话和流式事件。
- **证据**：
  - 文件路径：`AgentProxyHandler.java`、`fund_advisor_app/api.py`
  - 类 / 方法：`proxy`、`chat_stream`
  - 协议：`session/status/result/error/done`
- **可写入简历程度**：高。
- **适配 JD**：AI 应用后端、实时通信。
- **风险边界**：是 SSE 流式代理，不是 WebSocket 网关。

### 2. 可强推导的业务诉求

#### 诉求 1：慢且易波动的外部数据源不能拖垮 Java 入口

- **推导依据**：90 秒数据读取超时、虚拟线程、分批并行、零等待 Bulkhead。
- **可写边界**：可写“围绕阻塞型外部 I/O 做有界并发和超时治理”。
- **适配 JD**：Java 并发、服务稳定性。
- **不可夸大点**：没有线上 P99、QPS 或线程数对比。

#### 诉求 2：金融数值必须跨服务保持原始语义

- **推导依据**：原始 JSON 保存、`@JsonRawValue`、审计哈希、错误码分层。
- **可写边界**：可写“建立跨语言事实契约和审计透传”。
- **适配 JD**：数据平台、AI 应用后端。
- **不可夸大点**：不是监管合规认证。

#### 诉求 3：部分数据失败时仍需返回可解释结果

- **推导依据**：`rollUp`、`partial/stale/unavailable`、optional Tool warning。
- **可写边界**：可写“支持部分成功和显式降级”。
- **适配 JD**：高可用、聚合服务。
- **不可夸大点**：没有自动重试、熔断器或多机容灾。

#### 诉求 4：部署既支持同源，也支持前后端分离

- **推导依据**：`VITE_API_BASE`、`VITE_BASE_PATH`、精确 CORS 来源、GitHub Pages Workflow。
- **可写边界**：可写“支持同源与静态前端分离部署”。
- **适配 JD**：交付工程、平台工程。
- **不可夸大点**：仓库没有云资源编排和生产发布记录。

| 层面 | 已实现证据 | 结论 |

## 四、TOP 15 项目亮点

### 亮点 1：跨语言金融事实信封与原样透传

1. **亮点级别**：S
2. **架构师资深度层级**：L3
3. **亮点分类**：数据平台 / 一致性 / AI 应用架构
4. **结论归类**：【代码已实现】
5. **主导度判断**：负责核心模块实现与优化
6. **一句话简历表述**：设计跨 Java/Python 的 `ToolEnvelope` 事实契约，原样透传金融数据并附带来源、时效、warning 和 SHA-256 审计指纹。
7. **技术拆解**：Python 负责事实计算，Java 保存原始 JSON，只读提取状态元数据，避免多语言重复序列化或重算改变精度。
8. **代码证据**：`contracts/envelope.py`、`audit.py`、`ToolEnvelope.java`、`DatasetMeta.java`、`DashboardService.envelopeMeta`。
9. **架构价值**：解决跨语言职责与可信数据边界，不只是 DTO 映射。
10. **理论映射**：契约优先、单一事实来源、端到端审计；不能硬套事件溯源。
11. **JD 适配**：Java 后端、数据平台、AI 应用后端强相关。
12. **大厂口径**：字节看事实门禁；腾讯看治理；Google/Amazon 看边界与取舍。
13. **面试追问**：为何不用 Java DTO 全量反序列化？如何发现 Schema 漂移？失败信封如何处理？
14. **回答建议**：强调“Java 不拥有金融计算”，只抽取展示元数据，完整信封保持可追溯。
15. **风险提示**：不能称为金融监管审计或不可篡改账本。
16. **反吹牛审查**：面试官会要求指出 `@JsonRawValue` 和哈希生成位置；薄弱点是 Schema 版本演进策略仍有限。
17. **能写 / 不要写**：能写“事实契约、审计透传”；不要写“区块链级不可篡改”。

### 亮点 2：阻塞 I/O 场景的有界并行聚合

1. **亮点级别**：S
2. **架构师资深度层级**：L3

7. **技术拆解**：Overview 并行请求四类资产；基金产品并行请求四个模块；指数列表按并发上限分批，Data API Bulkhead 零等待拒绝过载。

### 亮点 4：业务错误、传输错误与部分结果分层

1. **亮点级别**：A
2. **架构师资深度层级**：L3
3. **亮点分类**：稳定性 / 错误治理
4. **结论归类**：【代码已实现】

7. **技术拆解**：业务错误保留原码，网络异常包装为可重试上游错误，可选模块失败不覆盖成功模块。
8. **代码证据**：`DashboardService.mapStatus/rollUp/transportFailureMeta`、`errors.py`、`validator.py`。
9. **架构价值**：避免“失败即空数据”导致错误业务判断。

11. **JD 适配**：Java 后端、稳定性平台。
12. **大厂口径**：腾讯/Amazon 匹配度高。
13. **面试追问**：为何 stale 不等于 unavailable？部分成功返回码是什么？是否重试？
14. **回答建议**：说明展示层需要保留数据质量，而 HTTP 200 不等于所有数据可用。
15. **风险提示**：当前无统一错误码注册中心。
16. **反吹牛审查**：验证 `rollUp` 真值表；薄弱点是跨服务错误版本兼容。
17. **能写 / 不要写**：能写“错误语义治理”；不要写“全链路容灾”。

## 五、最适合写进架构师简历的 8 条

### 1. 5 年及以上架构师通用版

- 设计 Java BFF 与 Python 数据服务的职责边界，以版本化事实信封承载来源、审计、时效和错误，Java 只做聚合与透传。
- 使用 Java 21 虚拟线程、`CompletableFuture` 和 Bulkhead 完成阻塞数据接口的有界并行聚合及部分失败降级。
- 使用 Redis Lua 构建原子固定窗口限流，并结合 fail-open 与下游容量门禁平衡入口可用性和过载保护。
- 使用 MySQL 联合唯一索引、事务和冲突重试实现匿名互动幂等写入。

### 2. AI 应用架构师版

- 将 Agent 作为 Java BFF 后的独立服务接入，Java 通过 SSE 原样转发状态与结果事件。
- 构建固定 LangGraph 工作流和注册 Tool 计划，避免模型直接决定数据访问权限。
- 对 Tool 结果执行数据策略、审计指纹和事实引用校验，模型不可生成或覆盖市场数值。
- 模型调用失败时回退为规则事实报告，区分必需工具失败和可选背景数据失败。

### 3. Agent / RAG / Workflow 架构师版

- 实现固定有向无环 Agent 工作流，覆盖分类、规划、调用、校验、综合和渲染节点。
- 通过 MCP 解耦基金事实工具与公网背景工具，并限制 Web 内容只能作为非数值背景。
- 使用结构化 Pydantic Schema 限制意图、事实引用和研究综合输出。
- 实现有界临时会话、会话级锁及 SSE 进度事件。
  **边界**：项目没有 RAG、向量库或多 Agent，不应在标题中写 RAG。

### 4. 平台架构师版

- 以 Java BFF 统一前端入口，隔离 Data API、Agent API、MCP 和基础设施。
- 通过环境变量、强类型配置和多阶段镜像统一跨语言运行方式。
- 建立跨服务错误语义、数据状态和审计元数据规范。
- 沉淀限流、SSE、静态托管、SPA fallback 和精确 CORS 等通用接入能力。

### 5. 分布式系统 / 存储架构师版

该项目不建议主打分布式存储架构师版本。可保守写：

- 参与 MySQL 数据约束、Redis 短期协调和跨服务数据契约设计。
- 针对外部服务调用实现有界并发、超时和部分失败处理。
- 通过单公网入口与容器网络隔离内部服务。
- 对跨语言数据读链路建立来源和哈希审计。

### 6. AI 性能优化架构师版

该项目不建议主打 AI 性能优化架构师版本。未发现模型量化、算子优化、通信优化、
GPU/AI 芯片适配、推理框架优化或 Benchmark/Profiler 证据。

- 构建 Java 21 + Spring Boot BFF，统一承接金融 Dashboard、产品元数据和 Agent SSE。

### S1：跨语言金融事实契约

**1. 一句话说人话**

Python 负责算金融数据，Java 负责把数据安全地交给页面；Java 不再算一遍，避免同一数字
经过两个系统后含义或精度发生变化。

**2. 业务背景，小白版**

用户看到的价格、估值和限额来自多个公开接口。如果 Java、Python、前端各自加工一次，
很难判断最终数字来自哪里。这个设计把“数据、来源、时间、校验结果、错误”装进同一个
信封，使每个展示值能回到源接口。代码没有证明监管或生产审计资质。

**3. 核心术语解释**

| 术语 | 小白解释 | 代码体现 |
|---|---|---|
| BFF | 专门服务前端的后端入口 | `DashboardController/Service` |
| ToolEnvelope | 装数据及来源证明的统一外壳 | Python/Java 同名契约 |
| Schema 校验 | 检查上游字段是否符合预期 | `validate_frame` |
| 审计指纹 | 对表格内容计算 SHA-256，便于确认输入版本 | `frame_fingerprint` |
| 原样透传 | 不拆散重组数据 JSON | `rawJson` + `@JsonRawValue` |

**4. 代码入口**

```text
DashboardController
  -> DashboardService
    -> DataApiClient
      -> Python Data API
        -> FundAdvisorToolAdapter / data_core
          -> Provider
        <- ToolEnvelope
      <- 原始 JSON
    -> DatasetMeta + @JsonRawValue
  -> React
```

**5. 核心文件**

| 文件 | 作用 | 阅读顺序 |
|---|---|---|
| `contracts/envelope.py` | 定义事实信封 | 1 |
| `audit.py` | Schema 和哈希审计 | 2 |
| `DataApiClient.java` | 请求并保留原始 JSON | 3 |
| `ToolEnvelope.java` | 只读提取元数据 | 4 |
| `DashboardService.java` | 状态聚合并返回前端 | 5 |

**6. 主链路**

1. Controller 校验查询参数。
2. Service 选择对应 Tool。
3. Data API 返回完整 Envelope。
4. Java 校验 JSON 对象并读取 `ok/queried_at/data_audit/error`。
5. Java 将原始 Envelope 嵌入响应，不修改数据字段。
6. 前端展示事实与审计元数据。

**7. 数据流**

```text
HTTP 参数 -> Tool 参数 -> Provider DataFrame -> Schema 校验
  -> frame_sha256 -> ToolEnvelope JSON
  -> Java DatasetMeta + 原始 Envelope -> 前端
```

**8. 为什么这样设计**

跨语言重复建模会增加字段遗漏和精度变化风险；完全不解析又无法做状态聚合。当前方案只
解析最少元数据，同时保留完整原文，在简单性和可用性之间取中间点。

**9. Trade-off**

1. 原样透传降低语义漂移，但 Java 编译期无法检查所有业务字段。
2. 统一 Envelope 增加响应体积，但换取来源和错误可追溯。
3. 单一事实来源限制 Java 灵活加工，但减少多端口径分裂。

**10. 异常与兜底**

- JSON 无法解析：转为 Data API 传输失败。
- 业务 `ok=false`：保留原始错误和已有审计。
- 数据 stale：映射为 `stale`，不冒充可用。
- 部分模块失败：外层返回 `partial`。
- 未发现 Schema 版本协商和灰度兼容机制，不能写成已实现。

**11. 架构师价值**

体现跨语言边界、数据所有权、错误语义和长期演进意识，明显高于普通 Controller 转发。

**12. 简历表述**

- 克制版：设计跨服务事实信封，原样透传金融数据及审计信息。
- 架构版：划分 Java 产品入口与 Python 数据计算边界，建立单一事实来源。
- 业务版：避免缺失数据被补零或上游错误被误判为标的不存在。
- AI 应用版：限制模型只解释已审计事实。
- 平台版：沉淀统一数据与错误契约。
- 分布式存储版：只可写数据契约，不写存储架构。
- AI 性能版：不适用。

### S2：Java 阻塞 I/O 的有界并行聚合

**1. 一句话说人话**

多个慢数据接口可以同时查，但不能无限同时查；系统既减少串行等待，也限制对下游的压力。

**2. 业务背景，小白版**

总览需要指数、ETF、基金和股票，产品页需要分析、档案、评级和状态。这些请求彼此独立，
串行会累加等待时间，无界并行又会压垮 Python 和外部数据源。

**3. 核心术语**

| 术语 | 小白解释 | 代码体现 |
|---|---|---|
| 虚拟线程 | JVM 管理的轻量线程，适合大量阻塞等待 | `setVirtualThreads(true)` |
| CompletableFuture | 把独立任务同时提交并等待汇总 | `overview/invokeAll` |
| Bulkhead | 给下游设置并发座位数，满了立即拒绝 | Resilience4j |
| 分批提交 | 一批完成后再提交下一批 | `invokeAll` |

**4. 代码入口**

```text
DashboardController
  -> DashboardService.overview/fundProduct/indices
    -> CompletableFuture / invokeAll
      -> DataApiClient.callTool
        -> Bulkhead
          -> Python Data API
```

**5. 核心文件**

| 文件 | 作用 | 顺序 |
|---|---|---|
| `WebBackendApplication.java` | 注册虚拟线程执行器 | 1 |
| `DashboardService.java` | 并行与分批聚合 | 2 |
| `DataApiClient.java` | 下游并发门禁和超时 | 3 |
| `BffProperties.java` | 并发和预算配置 | 4 |
| `DashboardServiceTest/DataApiClientTest` | 验证并发上限与立即拒绝 | 5 |

**6. 主链路**

1. 接收聚合请求。
2. 判断任务间无依赖。
3. 提交到虚拟线程执行器。
4. 按 `DASHBOARD_CONCURRENCY` 分批。
5. Data API 客户端再次通过共享 Bulkhead。
6. 汇总模块状态并返回。

**7. 数据流**

请求参数 → 多个 `Supplier` → `CompletableFuture` → RestClient → ToolEnvelope 列表 →
聚合响应。

**8. 为什么这样设计**

虚拟线程解决阻塞等待的线程成本，Bulkhead 解决下游容量，两者职责不同。分批提交避免
同一请求内部就把超过容量的任务立即拒绝。

**9. Trade-off**

1. 并行降低等待叠加，但增加瞬时下游压力。
2. Bulkhead 保护容量，但会牺牲部分请求完整性。
3. 虚拟线程简化阻塞代码，但数据库连接和 HTTP 连接仍是稀缺资源。

**10. 异常与兜底**

- Bulkhead 满：立即转为 `UPSTREAM_ERROR`。
- 单模块失败：返回独立 unavailable，聚合为 partial。
- 超时：RestClient read timeout。
- 未发现自动重试和熔断，避免把请求放大。

**11. 架构师价值**

体现能区分线程模型、连接资源和下游容量，不只是调用并发 API。

**12. 简历表述**

- 克制版：使用虚拟线程和 CompletableFuture 并行聚合独立数据模块。
- 架构版：在并行聚合外增加 Bulkhead 和批次门禁，显式约束下游容量。
- 业务版：单模块失败不阻塞其他可用模块返回。
- AI 应用版：可用于限制 Tool/Data API fan-out。
- 平台版：并发参数环境化。
- 分布式版：可写服务调用治理。
- AI 性能版：不适用。

**13. 三层追问**

1. 做了什么：四模块并行与指数分批。
2. 为什么：减少串行等待但不越过下游上限。
3. 扩大后：按接口独立 Bulkhead、指标驱动参数、超时预算传播。

**14. 验证问题**

面试官会要求解释 `maxWaitDuration(Duration.ZERO)` 和测试中的最大并发计数。

**15. 最易暴露点**

没有压测数据和连接池/线程参数的容量模型。

**16. 新人阅读路线**

配置 → 虚拟线程 Bean → `overview` → `invokeAll` → `DataApiClient` → 并发测试 →
Compose 服务资源。

**17. 风险边界**

可写“有界并发治理”；不能写“高并发系统”“性能提升 xx%”。

### S3：Agent 事实门禁

**1. 一句话说人话**

大模型可以解释数据，但必须先经过程序校验；没有来源证明的数据不能进入答案。

**2. 业务背景，小白版**

大模型擅长组织语言，但可能生成不存在的数字。金融场景下，系统把数据获取和最终表达
拆开：工具提供事实，固定流程校验，模型只做有限解释。

**3. 核心术语**

| 术语 | 小白解释 | 代码体现 |
|---|---|---|
| Agent | 按固定流程组合模型和工具的程序 | LangGraph |
| Tool | 获取数据的受控能力 | MCP |
| Workflow | 预先定义的执行步骤 | `StateGraph` |
| 事实引用 | 答案字段指向具体工具和审计哈希 | `FactRef` |
| 门禁 | 不满足规则就阻止进入下一步 | `validator.py` |
| RAG | 先检索知识库再回答 | 当前未实现 |

**4. 代码入口**

```text
Java AgentProxyHandler
  -> Python Agent API
    -> AgentChatService.stream
      -> fixed LangGraph
        -> Fund/Web MCP
        -> validate_tool_results
        -> validate_research_synthesis
        -> render_answer
```

**5. 核心文件**

| 文件 | 作用 | 顺序 |
|---|---|---|
| `fund_advisor_app/api.py` | SSE HTTP 入口 | 1 |
| `service.py` | 会话与事件流 | 2 |
| `graph.py` | 固定节点和条件边 | 3 |
| `nodes.py` | 每个执行节点 | 4 |
| `validator.py` | 事实与输出门禁 | 5 |
| `state.py` | 状态和结构化 Schema | 6 |

**6. 主链路**

1. 规则分类，低置信场景可选模型分类。
2. 代码生成注册 Tool 计划并限制数量。
3. Semaphore 控制 Tool 并发。
4. 校验 Envelope、数据策略和审计。
5. 提取带 `fact_id/audit_ref` 的事实。
6. 模型或规则生成结构化研究综合。
7. 删除无引用、含数字或确定性交易表达的模型内容。
8. SSE 返回结果。

**7. 数据流**

问题 → Intent/Entity → ToolCallSpec → ToolEnvelope → FactRef →
ResearchSynthesis → 校验后 AgentResponse → SSE。

**8. 为什么这样设计**

开放式 ReAct 更灵活，但工具选择和答案更难审计；固定图牺牲一部分自主性，换取可预测、
可测试和可拒绝。

**9. Trade-off**

1. 固定图可控，但复杂任务扩展较慢。
2. 结构化输出稳定，但限制自然语言表达。
3. Web 内容只能做背景，降低信息利用率但避免污染市场数字。

**10. 异常与兜底**

- 模型分类失败：保留规则结果。
- MCP 失败：生成错误 Envelope。
- 必需 Tool 失败：阻断研究综合。
- 可选 Web 失败：partial result。
- 研究模型失败：回退事实报告。
- 无跨会话持久化和节点恢复。

**11. 架构师价值**

体现对 AI 非确定性的工程化约束，适合 AI 应用后端，而不是模型算法岗。

**12. 简历表述**

- 克制版：实现固定 Agent 工作流和 Tool 结果校验。
- 架构版：将模型限制在结构化综合层，代码掌握工具和最终放行。
- 业务版：避免无来源市场数字进入回答。
- AI 应用版：固定 LangGraph + MCP + FactRef 审计门禁。
- 平台版：可写受控 Tool 接入基础。
- 分布式版：不适用。
- AI 性能版：不适用。

**13. 三层追问**

1. 做了什么：固定图和事实门禁。
2. 为什么：金融场景优先确定性。
3. 扩大后：增加 Eval、工具权限、节点 checkpoint 和事件持久化。

**14. 验证问题**

面试官会给一个无审计 Tool 结果，要求说明在哪一步被拦截；会问模型故障如何回退。

**15. 最易暴露点**

把固定 Agent 说成多智能体或 RAG，或说不清 Eval 缺口。

**16. 新人阅读路线**

Agent API → Service → Graph → Nodes → Policies → Validator → MCP Server → 测试。

**17. 风险边界**

能写 Agent/Tool/Workflow；不能写 RAG、多 Agent、长期记忆、模型推理优化或完整 Harness。

## 十、系统优化专项文档

### 1. 优化点总览

| 序号 | 优化方向 | 当前状态 | 证据 | 简历可写性 | 推荐 |
|---|---|---|---|---|---|
| 1 | 独立调用并行聚合 | 已实现 | 强 | 可写 | S |
| 2 | Bulkhead 容量隔离 | 已实现 | 强 | 可写 | S |
| 3 | 完整 Envelope TTL 缓存 | 已实现 | 强 | 可写 | A |
| 4 | 前端请求折叠 | 已实现 | 强 | Java 简历弱相关 | A |
| 5 | Redis Lua 限流 | 已实现 | 强 | 可写 | A |
| 6 | 部分结果降级 | 已实现 | 强 | 可写 | A |
| 7 | 按接口独立 Bulkhead | 未实现 | 中 | 不写已实现 | A |
| 8 | 分布式 Envelope 缓存 | 未实现 | 中 | 不写已实现 | A |
| 9 | 指标驱动压测与调参 | 未实现 | 弱 | 不写已实现 | S |
| 10 | Agent Eval 与节点恢复 | 未实现 | 中 | 不写已实现 | S |

### 2. 重点优化说明

#### 优化点 1：有界并行聚合

- **类型**：性能/稳定性；【当前已实现】；S。
- **原始问题**：独立外部调用串行会叠加等待，无界并行会压垮下游。
- **代码事实**：`DashboardService.invokeAll`、`DataApiClient` Bulkhead。
- **方案**：虚拟线程并行、按并发数分批、零等待拒绝、部分结果汇总。
- **Trade-off**：拒绝速度与结果完整性；并发增加与下游压力。
- **简历表述**：已可写。
- **追问**：依赖识别、线程池/连接池关系、超时预算。
- **反吹牛**：没有 P99 和吞吐对比。
- **能写 / 不要写**：核心链路并行优化 / 性能提升百分比。

#### 优化点 2：完整信封缓存

- **类型**：性能/成本；【当前已实现】；A。
- **原始问题**：同参数重复调用外部数据源。
- **代码事实**：`MemoryEnvelopeCache`、工具差异化 TTL、成功结果缓存。
- **方案**：规范化参数哈希作为 key，缓存完整 Envelope。
- **Trade-off**：降低 IO，但存在单实例、容量和击穿问题。
- **简历表述**：可写进程内 TTL 缓存，不写 Redis 分布式缓存。
- **追问**：失效、时效、并发 miss。
- **反吹牛**：没有命中率。
- **能写 / 不要写**：减少重复上游调用 / 缓存命中率 xx%。

#### 优化点 3：按接口独立隔离

- **类型**：稳定性；【建议补齐】；A。
- **原始问题**：当前所有 Data API 请求共享一个 Bulkhead，慢接口可能占满全局槽位。
- **代码事实**：`DataApiClient` 只有一个 `dashboard-data-api` Bulkhead。
- **方案**：按数据源或接口族拆 Bulkhead，并设置独立超时、指标和降级。
- **Trade-off**：隔离更细，但配置和监控成本上升。
- **简历表述**：当前不能写成已实现。
- **追问**：如何划分舱壁和预算？
- **反吹牛**：没有流量分布数据。
- **能写 / 不要写**：后续治理方案 / 已完成接口级隔离。

#### 优化点 4：分布式缓存与请求折叠

- **类型**：性能/成本；【建议补齐】；A。
- **原始问题**：进程内缓存无法跨实例共享，同 key 并发 miss 会重复调用。
- **代码事实**：`build_envelope_cache` 固定返回内存实现。
- **方案**：Redis 缓存完整 Envelope；增加 singleflight；失败不缓存；TTL 保持按工具配置。
- **Trade-off**：引入一致性、序列化、热点和 Redis 可用性问题。
- **简历表述**：当前不能写成已实现。
- **追问**：singleflight 首请求超时怎么办？
- **反吹牛**：未实现且无测量。
- **能写 / 不要写**：设计方向 / 已完成分布式缓存。

#### 优化点 5：可观测与性能基准

- **类型**：工程治理；【建议补齐】；S。
- **原始问题**：Actuator 已暴露指标，但没有按 Tool/状态/上游拆分的仪表盘和压测报告。
- **代码事实**：Micrometer/Prometheus 依赖与 endpoint 配置。
- **方案**：增加请求耗时、Bulkhead 拒绝、缓存命中、上游错误、SSE 活跃连接指标及
  Gatling/k6 基准。
- **Trade-off**：埋点和标签会增加维护成本，标签需控制基数。
- **简历表述**：当前只能写“具备指标暴露基础”。
- **追问**：指标如何驱动并发参数？
- **反吹牛**：不能报虚构结果。
- **能写 / 不要写**：完善可观测基础 / 完整监控告警闭环。

#### 优化点 6：Agent Eval 与恢复

- **类型**：AI 应用链路；【建议补齐】；S。
- **原始问题**：规则测试覆盖边界，但没有数据集、效果指标和节点恢复。
- **代码事实**：固定 Graph 与 Validator 已具备可测基础。
- **方案**：建立黄金问题集、事实引用正确率、拒答正确率；持久化 Run/Node 状态。
- **Trade-off**：评测和存储成本增加，指标设计需贴合业务风险。
- **简历表述**：当前不能写完整 Eval。
- **追问**：评什么、如何避免只评文案？
- **反吹牛**：无当前指标。
- **能写 / 不要写**：后续 Eval 方案 / 已构建效果闭环。

## 十四、1 分钟项目介绍

### 克制专业版

Fund Advisor 是一个基金和 ETF 研究工作台。我负责的重点是 Java 后端：使用 Spring Boot
作为唯一公网 BFF，向内连接 Python 数据和 Agent 服务。因为数据源调用是阻塞且延迟不
稳定的，我用 Java 21 虚拟线程和 CompletableFuture 并行聚合，再用 Bulkhead 控制下游
并发。金融数据通过统一 ToolEnvelope 原样透传，保留来源、错误和 SHA-256 审计指纹。
产品侧使用 MyBatis/MySQL 保存自选和互动，Redis Lua 做入口限流，Agent 通过 SSE 流式
代理。项目目前是可运行 MVP，没有虚构线上规模和性能指标。

### 更偏架构版

这个项目的核心设计是把产品入口、金融计算和模型解释拆开。Java BFF 负责接入、聚合、
存储和稳定性，Python Data API 负责事实计算，Agent 只能解释通过审计的数据。Java 侧
通过原始信封透传保持跨语言事实一致性，通过虚拟线程、Bulkhead 和部分结果模型治理慢
上游，通过 Redis/MySQL 分别处理短期流量协调和产品元数据一致性。

### 更偏业务结果版

项目把基金、ETF、指数、股票、QDII 限额和智能问答统一到一个入口，并保证缺失数据不
补零、源冲突不覆盖主值、上游错误不误报为“标的不存在”。Java 后端提供稳定的查询、
自选、互动和流式问答能力，数据来源与异常可以回溯到具体接口和审计指纹。

### AI 应用架构师版

项目通过 Java BFF 接入 Python Agent API，内部使用固定 LangGraph 和 MCP Tool。模型不
直接决定工具权限或市场数字，Tool 结果必须通过数据策略、审计指纹和事实引用校验；
研究模型不可用时回退为规则事实报告，Java 再通过 SSE 把节点状态和结果流式返回前端。

### 平台分布式架构师版

项目不属于大规模分布式存储。我会把它定位为跨语言后端平台：Java 统一外部入口，内部
服务通过明确契约协作，并对阻塞 I/O、并发容量、缓存、错误、限流和持久化一致性进行
治理。它能证明平台化思考，但不能证明大规模存储架构经验。

当前项目不适合用 1 分钟介绍主打 AI 性能优化。

## 十五、5 分钟深挖版本

项目背景是公开金融数据接口很多，但质量、字段和响应时间并不稳定，同时还希望提供
Agent 问答。如果直接让前端调用 Python，产品接口、数据计算和模型能力会耦合在一起，
也很难统一限流、错误和持久化。

因此系统采用 Java BFF + Python 数据/Agent 服务。Java 是唯一外部入口，负责 Dashboard
REST、自选与互动、Redis 限流、静态资源和 SSE；Python Data API 负责 AKShare 等数据源
及确定性计算；Agent API 通过固定 LangGraph 调用 MCP。这个边界的核心规则是：Java 和
模型都不能生成或改写金融事实。

第一个难点是慢数据源聚合。总览需要四类资产，基金产品需要四个独立模块。我用 Java 21
虚拟线程和 CompletableFuture 并行执行，但并行线程多不代表下游容量无限，所以
DataApiClient 再加共享 Bulkhead，超出并发上限立即拒绝；指数批量查询还按上限分批，
避免同一请求自我挤占。单模块失败后不会把整个响应伪装成成功，而是保留模块状态并聚合
为 partial、stale 或 unavailable。这里没有压测数据，所以我只描述机制和测试结论。

第二个难点是跨语言数据可信。Python 返回的 ToolEnvelope 同时包含数据、来源、查询时间、
warning、错误和 frame_sha256。Java 保存原始 JSON，用 JsonNode 只读提取页面需要的
元数据，再通过 JsonRawValue 原样嵌入响应。这样既能由 Java 做产品聚合，又不会因为 DTO
转换、四舍五入或字段遗漏改变金融事实。多源校验也只追加 warning，不平均或修正主值。

第三个难点是入口稳定性和写入一致性。Redis 限流通过 Lua 把 INCR 和 EXPIRE 放在一次
原子执行中；Redis 故障时选择 fail-open，因为它不是事实源，而 Data API Bulkhead 仍能
保护容量。匿名投票使用 MySQL 联合唯一索引定义“一客户端、一主题、一个选择”，服务层
先 update，再 insert，遇到并发唯一键冲突后再次 update。这个方案比 select-then-insert
更能抵抗竞争条件，但还没有高冲突压测。

Agent 是附属能力。Java 用 StreamingResponseBody 和 JDK HttpClient 逐块代理 SSE，
过滤 hop-by-hop Header、限制请求体并关闭上游流。Python 内部是固定流程，不是开放式
ReAct：代码决定 Tool 和状态分支，模型只做结构化综合；缺审计、Web 数值越权或确定性
交易表达都会被拦截。项目没有 RAG、多 Agent、持久化 Workflow 或模型推理优化。

工程上使用 Flyway 管理 MySQL 结构，Actuator/Micrometer 暴露健康与 Prometheus 指标，
Docker Compose 编排七个服务且只暴露 Java。测试覆盖 Java 控制器、并发、限流、SSE、
数据库服务，Python 覆盖数据与 Agent 契约，Playwright 覆盖六个视口和暗色模式。后续最
值得补的是性能基准、按接口隔离、跨服务 Trace、认证权限和 Agent Eval。

## 十六、最终结论

1. **最值得打的三张牌**：跨语言事实契约；虚拟线程 + Bulkhead 有界并发；Redis/MySQL
   稳定性与一致性治理。
2. **最不该硬吹的三点**：高并发规模；大规模分布式存储；模型推理/RAG。
3. **5 年及以上架构师定位**：强调边界、错误模型、并发容量和 trade-off，不强调框架数量。
4. **AI 应用架构师定位**：强调固定 Workflow、Tool 门禁、事实引用和 SSE 服务化。
5. **Agent/RAG/Workflow 定位**：可主打 Agent/Workflow，明确没有 RAG。
6. **平台架构师定位**：可突出统一入口、契约、配置、容器交付和治理组件。
7. **分布式/存储定位**：不建议主打，只保守表达 MySQL、Redis 和跨服务读链路。
8. **AI 性能优化定位**：不适合，缺少任何模型底层证据。
9. **只能写三条**：BFF 事实契约、有界并行聚合、Redis/MySQL 治理。
10. **只能讲一个点**：讲“为什么虚拟线程之后仍需要 Bulkhead，以及如何返回部分结果”。
11. **最优先补三项**：性能压测与容量模型、跨服务 Trace、Agent Eval。
12. **推荐岗位顺序**：Java 后端 > AI 应用后端 > 平台后端 > Agent 工程 >
    分布式存储 > AI 性能优化。
